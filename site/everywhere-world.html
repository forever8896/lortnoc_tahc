World ID · IDKit 4.3 · verify, don't trust

Real humans — and real passports — as a key.

In Everywhere, World ID is one of the keys that can open a hidden post: verified humans, Selfie Check, or citizens of a country via passport Identity Check. It is only ever a reader rule — never needed to write, never an account, never a meter.

What the reader sees

Extension ⚙ → Keys → World ID → Verified human, Selfie, or Nationality → Prove. World's own widget opens, they scan it with World App, and it's done — once. From then on, every post for verified humans (or for their nationality) simply opens when it appears on a page. No QR per post, and no post ever reveals that it asks for World ID: it's sealed, and only a reader whose keys open it learns what it asked for.

Step by step — connecting World ID once

The gate signs a request, bound to this reader

The extension asks the gate (POST /connect/world/challenge). The gate signs an RP request with its RP signing key (signRequest), action lortnoc-connect, and a signal = request id ‖ the reader's keyring key — so a proof can only ever be used for this one request. Environment: sandbox for phones, staging for World's simulator.

World's own widget, in an extension tab

IDKitRequestWidget from @worldcoin/idkit runs in its own tab (it needs ≥ 1024 px; below that it drops the QR for a deep link). Presets: proofOfHuman, selfieCheck, or identityCheck with nationality = ISO alpha-3 and a legacy_signal (see findings).

World App proves it

The reader scans with World App (World ID Sandbox app on staging). The proof returns to the widget over World's bridge; the widget's handleVerify hands it to the extension, which sends it to the gate (POST /connect/world). The widget shows success only after the gate accepted it.

The gate checks everything, twice

Its own checks first (below), then both World's v4 verify API and the WorldIDVerifier contract on World Chain, asked through three RPCs — at least two must say valid and none invalid.

A keyring session

The gate remembers only what was proven: a per-action nullifier per credential (poh, selfie, nat.DNK) behind a bearer token the extension keeps. No name, no document data, no IP.

Posts open by themselves

When a page is scanned, the extension asks the gate about every candidate at once (POST /unlock). For each sealed post whose rule the reader's connected credentials satisfy, the gate releases its key piece — sealed to a one-time key of that reader.

Spaces: bans that stick to a person

In a space ("Verified humans of lentil-club.space"), the gate turns the World ID nullifier into a member pseudonym — member- + 12 hex of an HMAC with a gate secret — stable per space, unlinkable across spaces. Members can sign posts as that pseudonym (the gate countersigns only the hash). The owner bans a pseudonym in the space's ENS record; because World ID is one per person, the same human can't return with a new account.

What we found integrating it

A missing v4 signal is zero, not hash(""). Identity Check takes no signal, so IDKit omits signal_hash; World's portal treats that as 0x0 (request-schema.ts). Passing hash("") made every passport proof fail on-chain. Fixed in verifierArgs(), with regression tests.
The Sandbox app answers only environment: sandbox (docs) — a staging request shows "Verification unavailable". The gate issues sandbox for phones and staging only when the reader asks for the simulator.
Identity Check falls back to World ID 3.0 by design. IDKit's preset sets allow_legacy_proofs_override: Some(true) (preset.rs), so a phone holding an older document credential answers with a v3 secure_document proof. We accept v3 for nationality only, bound to the request through legacy_signal, verified by World's API (v3 has no on-chain verifier).
A tab closed with the browser's × can't tell anyone — the extension watches for it, and every step lands in the gate's activity trail.
